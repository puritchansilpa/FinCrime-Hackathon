# Let identifiers decide, let models read

Across academic work, regulation, industry practice and open-source tools, sanctions/PEP hit adjudication follows one design. A high-recall name matcher generates candidates. A decision layer then compares *secondary identifiers* (DOB, nationality/country, entity type, ID numbers, death status) against the **full** list entry. Clear non-matches are discounted with a documented reason, multi-identifier agreement is escalated, and everything ambiguous goes to a human. Name similarity alone is weak evidence: OFAC's own search tool scores names only, and phonetic codes used as a match decision produce mostly false hits. The strongest independent evidence for AI is a 2025 Federal Reserve staff paper, which found that LLMs cut false positives by **92%** and raised detection by **11%** against the best fuzzy matcher, but ran more than **four orders of magnitude slower**, which argues for a cascade. On the public OpenSanctions Pairs benchmark, GPT-4o reaches **99.0% F1** against 91.3% for a production rule/regression matcher. LLMs still fail in documented ways: they fabricate values for required fields, normalise dates poorly, overweight one matching attribute, and are vulnerable to prompt injection from web content. For a hackathon with a fixed SOP and an asymmetric loss where clearing a true match is the worst error, the evidence supports three things. LLMs should *extract* typed, evidence-quoted facts. Deterministic SOP rules should *decide*. DIFFERENT_ENTITY should be issued only on a positive, well-attributed conflict, never on missing data, so that uncertainty falls into REVIEW. That is the Fellegi-Sunter three-zone design that regulators already expect.

## Name similarity finds candidates; it cannot clear them

The best independent comparison of name matchers (Christen 2006, four real name datasets) found that phonetic encoding plus exact code comparison averaged F-measures of only about **0.28–0.62**. String "pattern matching" methods did much better: Jaro-Winkler reached up to **0.89** and longest-common-substring up to **0.92**. Christen's explicit recommendation is that phonetic codes "should not be used" as the matcher, only for blocking ([Christen 2006](https://users.cecs.anu.edu.au/~Peter.Christen/publications/tr-cs-06-02.pdf)). He also found "no single best technique". Small threshold changes caused "dramatic drops" in quality, and in one dataset **43.5% of true matched pairs differed by 6–10 edits**, so any pure edit-distance cutoff loses real variants ([Christen 2006](https://users.cecs.anu.edu.au/~Peter.Christen/publications/tr-cs-06-02.pdf)). For multi-token names, a TF-IDF-weighted token comparison with a Jaro-Winkler inner metric ("SoftTFIDF") performed best on average ([Cohen et al. 2003](https://www.cs.utexas.edu/~ai-lab/pubs/kdd03.pdf)). The practical point is that common tokens ("Mohammed", "Trading", "Ltd") must be down-weighted.

OFAC's own Sanctions List Search shows what a name-only score is. It pre-filters by first letter and at least 50% edit similarity, then reports the higher of a whole-string Jaro-Winkler score and a per-part Jaro-Winkler + Soundex composite. It recommends no threshold ([OFAC FAQ 249](https://ofac.treasury.gov/faqs/249)). OpenSanctions reverse-engineered the scorer to a SimMetrics.NET Jaro-Winkler that **always applies the prefix bonus**. Modern libraries such as rapidfuzz and jellyfish only apply it when Jaro exceeds 0.7, so they reproduce OFAC scores only about 90% of the time, against about 96% for a faithful emulator ([OpenSanctions 2026](https://www.opensanctions.org/articles/2026-07-01-ofac-matcher/)). A high OFAC-style score therefore says nothing about DOB, country or entity type, and the SOP's identifier checks must carry the decision.

Cross-cultural structure is where both misses and false positives come from. Name order flips for East Asian names. Arabic names add or drop nasab components. Abjad scripts omit vowels. One person can appear as "Mohammed Al-Fulan", "Mo Alfolan" or "Mike Fuller" ([OpenSanctions 2025](https://www.opensanctions.org/articles/2025-06-24-name-matching)). OpenSanctions' logic-v2 matcher compares first names only to first names and family names only to family names, lets middle initials match middle names, and transliterates only where romanisation is reliable. It relies on a dictionary of **161,000 Wikidata name items with about 1.16M spellings** ([OpenSanctions logic-v2](https://www.opensanctions.org/articles/2025-09-11-logic-v2)). For companies, it maps legal forms (OAO, JSC, AG) to one concept, treats words like "Holding" as soft stopwords, and fuzzy-matches only the distinctive core. Whole-string Levenshtein rates "Sparkles Business Corporation" vs "Sporks Business Corporation" at **89%**, but the cores alone score **50%** ([OpenSanctions logic-v2](https://www.opensanctions.org/articles/2025-09-11-logic-v2)). The enforcement record gives the regression tests:

- JPMorgan's filter missed names with hyphens, initials and extra tokens ([Law.com](https://law.com/corpcounsel/2018/12/03/ofac-settlement-highlights-limitations-of-search-software)).
- Apple missed "SIS d.o.o." vs "SIS DOO" ([Orrick](https://media.orrick.com/Media%20Library/public/files/insights/2021/2021-03-31-compliance-lessons-in-recent-office-of-foreign-assets-control-enforcement.pdf)).
- Payoneer's "weak algorithms" let close SDN matches go unflagged ([OFAC release](https://ofac.treasury.gov/media/911571/download)).

These failures matter for the hackathon in one specific way. The "verified-name mismatch" reason code must only fire after this normalisation (order, particles, initials, legal suffixes, transliteration). Otherwise a formatting difference gets treated as a different person, which is exactly the worst-case error.

## Fellegi-Sunter's three zones are the SOP in mathematical form

Probabilistic record linkage (Fellegi & Sunter 1969) gives each field an agreement weight log2(m/u) and a disagreement weight log2((1−m)/(1−u)), adds them up, and sets **two thresholds**. Above the upper one is a link, below the lower one is a non-link, and the band between goes to clerical review ([Splink FS guide](https://moj-analytical-services.github.io/splink/topic_guides/theory/fellegi_sunter.html); [DOI](https://doi.org/10.1080/01621459.1969.10501049)). These three zones are SAME_ENTITY / DIFFERENT_ENTITY / REVIEW. When clearing a true match is the worst error, the tolerated false-non-link rate should be close to zero. That pushes the lower threshold down and widens REVIEW. Auto-clearing is then justified only by fields with large *disagreement* weights, such as a conflicting full DOB or a different entity type. The model also explains itself field by field ("DOB disagreement contributed −6.6 bits"). Its known weakness is the assumption of conditional independence between fields, which is "rarely true in practice" ([Splink FS guide](https://moj-analytical-services.github.io/splink/topic_guides/theory/fellegi_sunter.html)). Name frequency should also adjust the u-probabilities, because agreement on "Wang" is much weaker evidence than agreement on a rare surname.

OpenSanctions' production weights are a ready-made, citable version of this policy. In logic-v2, name_match carries 1.0 and strong identifiers (LEI, IMO, INN, BIC) carry 0.95. Penalties are **−0.25 for a day-level DOB conflict, −0.15 for a year-level conflict, −0.20 for country mismatch and −0.20 for gender mismatch**, with a default threshold of 0.7 ([OpenSanctions matcher](https://www.opensanctions.org/matcher/)). Crucially, these features fire only on *disjoint* values. Missing data is not penalised, which matches OFAC FAQ 5's logic that "few details align" supports discounting while unknowns call for more information ([OFAC FAQ 5](https://ofac.treasury.gov/faqs/5)). OpenSanctions' own tuning notes say that passing even a birth year "substantially reduces false positives" ([Tuning docs](https://www.opensanctions.org/docs/api/tuning/)).

The customer side is its own entity-resolution problem when tables share no key. The standard pipeline is blocking, then pairwise scoring, then clustering. Naive transitive closure (connected components) over-merges, because one bad link can fuse unrelated people ([Rahm & Peukert](https://dbs.uni-leipzig.de/file/large-scale-ER.pdf)). A shared address or phone indicates a *relationship* such as a household or corporate service address, not identity ([Senzing](https://senzing.com/redhorse-graphaware-entity-resolved-knowledge-graphs/)). Splink (MIT, v5.0.0, Sept 2026) runs unsupervised Fellegi-Sunter linkage on DuckDB, links about 1M records in roughly a minute on a laptop, and supports term-frequency adjustment ([Splink docs](https://moj-analytical-services.github.io/splink/index.html); [PyPI](https://pypi.org/project/splink/)). Splink 5 changed its API, so most tutorials and LLM-generated code target v4 ([gist](https://gist.github.com/RobinL/c6d56a27d8f83c40b6b09643c0fa5d14)). Survivorship into a golden record is risky for screening because it can discard the very alias or DOB that matches the list entry. The safer approach keeps every source value and flags internal conflicts.

## Machine-learning triage works only as selective classification

Peer-reviewed, quantified evidence on sanctions *alert* classification is thin. Kim & Yang (2024) report baseline false-positive rates **above 90%**. They found that NLP enhancements reduced false negatives but *increased* false positives, with the threshold driving the trade-off ([Frontiers in AI](https://www.frontiersin.org/articles/10.3389/frai.2024.1374323/full)). The nearest bank-data study, Jullum et al. (2020), uses gradient-boosted trees on DNB transaction-monitoring alerts. It shows that investigated-but-not-reported alerts are valuable negative labels, which is the analogue of using historical analyst "false positive" dispositions as training data ([Emerald](https://emerald.com/insight/content/doi/10.1108/JMLC-07-2019-0055/full/html)). Vendor claims cluster at **50–92% false-positive reduction**: SymphonyAI claims 83–92% with "100% true positive retention", Quantexa 75% and Precisely 58%. None discloses baselines or audited recall ([SymphonyAI](https://www.symphonyai.com/financial-services/screening); [Quantexa](https://www.quantexa.com/solutions/aml/); [Precisely](https://www.precisely.com/app/uploads/2020/05/CS_Blinded_US-Based-Retail-Bank_200505_E_final.pdf)). An SSRN ensemble reporting **93.5% recall at 1% FPR** shows the trap: a good balanced metric that would still clear about one true hit in fifteen ([SSRN](https://papers.ssrn.com/sol3/Delivery.cfm/7266559.pdf?abstractid=7266559&mirid=1)).

The right formulation is selective classification with a reject option. Chow's Bayes-optimal rule abstains when the top posterior falls below a cost-dependent bound, and this requires calibrated probabilities ([Dietterich slides](https://web.engr.oregonstate.edu/~tgd/talks/dietterich-deeplearn-2021-rejection.pdf); [Franc et al.](https://ar5iv.labs.arxiv.org/html/2101.12523)). El-Yaniv & Wiener formalise the risk-coverage trade-off, including the zero-risk case ([JMLR 2010](https://jmlr2020.csail.mit.edu/papers/volume11/el-yaniv10a/el-yaniv10a.pdf)). In practice, set the auto-clear threshold on held-out labelled data so that no true match falls below it. Then measure the automation rate (coverage) at that point, not AUC or F1. One statistical consequence follows directly. With zero misses among *n* true matches, the 95% upper bound on the miss rate is about 3/*n*. The number of labelled **true** matches, not total alerts, therefore limits how strongly the team can claim safety. I found no source applying conformal risk control to screening, so treat it as a promising but unvalidated technique.

## LLMs are strong matchers but unreliable deciders

The independent evidence favours LLMs as matchers. Allen & Hatfield (Federal Reserve, FEDS 2025-092) compared four LLM families against common fuzzy matchers on name and address similarity. Across realistic thresholds, the LLMs cut false positives by **92%** and raised detection by **11%**, and smaller models in the same families performed comparably. However, the LLMs were **more than 10,000x slower**. A cascade that sent only uncertain cases to the LLM was about twice as fast as LLM-only, with similar accuracy ([FRB](https://www.federalreserve.gov/econres/feds/can-llms-improve-sanctions-screening-in-the-financial-system-evidence-from-a-fuzzy-matching-assessment.htm)). This covers name/address matching, not end-to-end adjudication with DOB and adverse media. On OpenSanctions Pairs (755,540 expert-labelled pairs, 293 sources, Latin/Cyrillic/Arabic), GPT-4o scored **99.0% F1** and a local DeepSeek-R1-Distill-Qwen-14B **98.2%**, against **91.3%** for nomenklatura's regression matcher. Rules tended to over-match, and LLMs struggled with cross-script transliteration ([arXiv 2603.11051](https://arxiv.org/abs/2603.11051)).

General entity-matching research adds the operational detail:

- **Zero-shot strength.** Zero-shot GPT-4 reaches ≥89% F1 on 5 of 6 benchmarks, and every LLM beats transferred fine-tuned matchers on unseen entities by at least 8 points ([Peeters et al., EDBT 2025](https://arxiv.org/html/2310.11244v4)).
- **Rules in the prompt.** Hand-written matching rules in the prompt *cost* GPT-4 1–3 points, though they help weaker models ([Peeters et al.](https://arxiv.org/html/2310.11244v4)). This argues for keeping SOP rules in code.
- **Failure modes.** Errors come from "partial information matches" and from overemphasis on a single matching attribute ([Peeters et al.](https://arxiv.org/html/2310.11244v4)). In this setting, that means a matching name outweighing a conflicting DOB.
- **Select framing.** Choosing among candidates ("select") beats isolated pairwise yes/no decisions by **17.58% F1** on average ([ComEM, COLING 2025](https://arxiv.org/html/2405.16884v3)). This fits picking which customer record, if any, a hit refers to.
- **Cost.** Per-pair zero-shot prices (Aug 2024) ranged from about **$0.00006** (GPT-4o-mini) to **$0.0047** (GPT-4) ([Peeters et al.](https://arxiv.org/html/2310.11244v4)). Latency and determinism, not dollars, are the constraints.

Extraction is where silent errors enter. Schema-constrained JSON fixes syntax but not semantics. The documented failure is a model filling a *required* date field with a plausible invented value, returning "perfect JSON" that is wrong. The fix is nullable fields plus validators ([Towards Data Science](https://towardsdatascience.com/your-llm-can-return-perfect-json-and-still-be-wrong/); [LLMStructBench](https://arxiv.org/html/2602.14743v1)). Temporal normalisation remains weak: average accuracy is about **0.62** across six models on SCATE-style normalisation, with generating code beating direct generation by more than 10 points ([arXiv 2507.06450](https://arxiv.org/html/2507.06450v1)). Relative expressions such as "aged 54" or "last year" must be anchored to a publication date, which is exactly where accuracy drops. Verbalised LLM confidence is systematically overconfident ([arXiv 2510.20460](https://arxiv.org/html/2510.20460v1)). Neither self-consistency nor cross-model agreement is reliable as a *standalone* abstention signal ([arXiv 2607.08065](https://arxiv.org/pdf/2607.08065)). FTI warns that GenAI outputs "may... vary between runs" and recommends that the interpretable signal come from rules or models, with GenAI only writing the narrative ([FTI 2026](https://www.fticonsulting.com/insights/articles/beyond-speculation-applying-ai-sanctions-compliance)).

Namesake-heavy web results are an old problem. The WePS campaigns (2007–2010) clustered the top ~100 web pages for an ambiguous name by real individual and then added attribute extraction. Simple agglomerative clustering was strong, and B-Cubed was the right metric ([SemEval-2007](https://preview.aclanthology.org/fix_video/S07-1012.pdf); [arXiv 1401.4590](https://arxiv.org/pdf/1401.4590)). LLM-era entity linking works best when the model gets a short reference profile and a multiple-choice question ([arXiv 2402.06738](https://www.arxiv.org/pdf/2402.06738)). The most concrete practitioner account is OpenSanctions (May 2026), which runs an LLM "analyst" and an adversarial "senior reviewer" and sends disagreements to humans. The reviewer vetoed merging two same-named Chinese NPC deputies from different delegations. The LLM rejected two Austrian councillors with a 0.97 structured similarity because they came from different villages. Models struggled with career transitions, such as a former Defence Minister later becoming Prime Minister. The same account warns of planted prompt injections in biographies and of manufactured adverse coverage ([OpenSanctions](https://www.opensanctions.org/articles/2026-05-12-llms-screening/)). No published precision or recall exists for LLM namesake rejection in adverse-media results. That is the least-validated part of this pipeline.

## Regulators want a reason for each alert, not a particular algorithm

OFAC FAQ 5 is the closest thing to a public SOP. Review the **full list entry**, compare aliases, DOB, nationality, ID numbers and addresses, and treat the match as possibly invalid "if few details align". Escalate when several align, **document the steps and information relied on**, and remember that OFAC "does not confirm potential matches or false positives" ([OFAC FAQ 5](https://ofac.treasury.gov/faqs/5)). MAS requires a documented justification for each dismissal, four-eyes and QA checks, and rules for name order and conflicting tokens. It names **dismissing alerts on a consolidated basis** as poor practice ([MAS 2022](https://www.mas.gov.sg/publications/monographs-or-information-paper/2022/strengthening-aml-cft-name-screening-practices); [Waystone](https://compliance.waystone.com/mas-paper-on-strengthening-aml-cft-name-screening-practices/)). The EBA guidelines, applicable from 30 Dec 2025, require procedures for alerts where "an unambiguous determination is not possible", which is the regulatory basis for a REVIEW outcome ([EBA](https://www.eba.europa.eu/publications-and-media/press-releases/eba-issues-final-guidance-internal-policies-procedures-and-controls-ensure-implementation-union-and)). The FCA's review of more than 90 firms faulted both over-sensitive and under-sensitive calibration, large alert backlogs, and firms that could not explain why alerts did not fire ([FCA 2023](https://www.fca.org.uk/publications/good-and-poor-practice/sanctions-systems-and-controls-firms-response-increased-sanctions-due-russias-invasion-ukraine)). OFAC penalised Payoneer partly for **auto-releasing flagged payments during backlogs** ([OFAC release](https://ofac.treasury.gov/media/911571/download)).

On AI specifically, FATF and the Wolfsberg Group require explainability, human oversight and accountability ([FATF Suggested Actions](https://www.aml.gov.sa/en-us/GuidanceReports/Suggested%20Actions%20New%20Technologies%20AML-CFT.pdf); [Wolfsberg AI principles](https://www.regulationtomorrow.com/2022/12/the-wolfsberg-group-publishes-principles-for-using-artificial-intelligence-and-machine-learning-in-financial-crime-compliance/)). In the US, OCC Bulletin 2026-13 (April 2026) **rescinded SR 11-7 and the 2021 BSA/AML model-risk statement**. It excludes deterministic rule-based processes from the definition of a model and explicitly places generative and agentic AI out of scope pending a future RFI ([OCC 2026-13](https://occ.treas.gov/news-issuances/bulletins/2026/bulletin-2026-13.html)). That leaves LLM-based clearing in a guidance gap, which strengthens the case for deterministic rules as the decision of record. No regulator publishes a DOB tolerance window, a primary/secondary identifier ranking, or an acceptable false-negative rate. Conventions such as "±1–2 years for year-only DOBs" are institutional choices, not requirements. Industry false-positive rates of 85–95% are likewise vendor figures with no stated method ([Sayari](https://sayari.com/resources/blog/financial-industry-compliance-challenges/)).

## Prioritised recommendations for the hackathon system

The design principle that follows from all of the above is **asymmetric evidence**. SAME_ENTITY requires positive agreement on the SOP's confirmation keys. DIFFERENT_ENTITY requires a positive, well-attributed *conflict* on a discriminating field. Everything else, including missing data, extraction doubt, internally inconsistent customer records and namesake-only web evidence, is REVIEW. In Fellegi-Sunter terms, this sets the false-non-link tolerance close to zero and accepts a wider review band.

| Priority | Recommendation | Rationale |
|---|---|---|
| **P0** | **Rules decide; the LLM only extracts.** Encode the SOP as an ordered, deterministic decision table in code. The LLM outputs typed facts (DOB, death date, nationality/country, entity type, activity dates, aliases), each with the verbatim source span, a source tag (`hit_profile`, `customer_table`, `web_result`), and `null` when absent. Validate that every span actually occurs in the source text. | Avoids rule-in-prompt degradation, fabricated required fields and run-to-run variance. Gives an OFAC-FAQ-5-style audit trail ([Peeters](https://arxiv.org/html/2310.11244v4); [TDS](https://towardsdatascience.com/your-llm-can-return-perfect-json-and-still-be-wrong/); [FTI](https://www.fticonsulting.com/insights/articles/beyond-speculation-applying-ai-sanctions-compliance)) |
| **P0** | **Absence never clears.** A missing DOB or country on either side cannot produce DIFFERENT_ENTITY. Only *disjoint* values can (logic-v2 semantics). | Matches OFAC FAQ 5 and OpenSanctions penalty design ([OFAC FAQ 5](https://ofac.treasury.gov/faqs/5); [matcher](https://www.opensanctions.org/matcher/)) |
| **P0** | **Only hit-attributed facts may clear.** Conflicts that justify DIFFERENT must come from the hit's own profile/notes or a web result that is first anchored to the hit (e.g. matching DOB *and* role/location). A namesake's DOB in a search result must never be read as the hit's DOB. | The search results are mostly about namesakes. Misattributing one is a direct path to clearing a true match ([WePS](https://preview.aclanthology.org/fix_video/S07-1012.pdf); [OpenSanctions](https://www.opensanctions.org/articles/2026-05-12-llms-screening/)) |
| **P0** | **Normalise names before the verified-name check.** Fire "verified-name mismatch" only after case/diacritic folding, transliteration, token reordering, particle and initial handling, and legal-suffix canonicalisation, comparing the distinctive core with IDF weighting. Near-misses go to REVIEW. | Enforcement failures (hyphens, initials, d.o.o./DOO) and the over-rewarding of common tokens ([Law.com](https://law.com/corpcounsel/2018/12/03/ofac-settlement-highlights-limitations-of-search-software); [logic-v2](https://www.opensanctions.org/articles/2025-09-11-logic-v2)) |
| **P1** | **Make dates deterministic and tiered.** The LLM returns the raw date string. Code parses it (dateparser) to a precision level (day/month/year/range). Full-date conflicts clear. Year-only or "circa" values clear only outside an explicit tolerance. Day/month transpositions and single-digit typos go to REVIEW. Temporal impossibility (e.g. a hit active before the customer was born) and deceased checks use the same parsed intervals, with relative ages anchored to the publication date. | LLM temporal normalisation is about 0.6–0.7 accurate. Day-level conflicts outweigh year-level ones ([arXiv 2507.06450](https://arxiv.org/html/2507.06450v1); [matcher weights](https://www.opensanctions.org/matcher/)) |
| **P1** | **Resolve the customer conservatively without a shared key.** Link tables with Splink or a simple blocked Fellegi-Sunter scorer (name tokens + DOB, term-frequency adjusted). Never treat shared address or phone as identity. Keep every source value. If the customer's own records disagree on DOB or country, route to REVIEW rather than choosing one. | Over-merging under connected components; survivorship can drop the matching variant ([Rahm & Peukert](https://dbs.uni-leipzig.de/file/large-scale-ER.pdf); [Splink](https://moj-analytical-services.github.io/splink/index.html)) |
| **P1** | **Fix rule precedence and emit one reason per hit.** For example: entity-type mismatch, then attributed deceased/temporal impossibility, then full-DOB conflict, then location conflict, then verified-name mismatch, all leading to DIFFERENT. Name + DOB (+ country), or company name + country, leads to SAME. Anything else is REVIEW. If a confirming and a conflicting signal co-occur, output REVIEW. Log the full evidence vector, not just the winning code. | Per-alert justification, no consolidated dismissal, an explicit "no unambiguous determination" path ([MAS](https://compliance.waystone.com/mas-paper-on-strengthening-aml-cft-name-screening-practices/); [EBA](https://www.eba.europa.eu/publications-and-media/press-releases/eba-issues-final-guidance-internal-policies-procedures-and-controls-ensure-implementation-union-and)) |
| **P1** | **Treat web text as untrusted.** Pass only extracted facts and quoted spans to the decision layer, and never execute instructions found in pages. | Planted prompt injections and manufactured adverse media are flagged risks ([OpenSanctions](https://www.opensanctions.org/articles/2026-05-12-llms-screening/)) |
| **P2** | **Use disagreement as an abstention trigger.** Run extraction twice (or with two models/prompts) at temperature 0. Any disagreement on a field that would trigger DIFFERENT downgrades the result to REVIEW. Ignore the model's self-reported confidence. | Overconfident verbalised confidence. Dual-LLM-plus-human pattern ([arXiv 2510.20460](https://arxiv.org/html/2510.20460v1); [OpenSanctions](https://www.opensanctions.org/articles/2026-05-12-llms-screening/)) |
| **P2** | **Cascade for cost and latency.** Run the deterministic scorer first. Call the LLM only for hits that need extraction from notes or web text, and use a small model for the bulk. | Fed result: cascade about 2x faster at similar accuracy, and small models are comparable ([FRB](https://www.federalreserve.gov/econres/feds/can-llms-improve-sanctions-screening-in-the-financial-system-evidence-from-a-fuzzy-matching-assessment.htm)) |
| **P2** | **Evaluate on the worst error.** Report false-clear count and rate on true matches first, then the automation rate (share not in REVIEW), then accuracy. ## Conclusion

The field's main shift is not that machine learning beats rules. It is a division of labour. Name similarity, deterministic or embedding-based, finds candidates. Secondary identifiers make the decision. LLMs are now the best tool for turning free-text notes and messy web pages into those identifiers, and benchmarks show that they match names better than fuzzy logic. Their documented failures (invented values, weak date handling, overweighting one attribute, injection) all point the same way: towards wrongly confident decisions. That makes them a poor *final* arbiter when clearing a true match is the costliest mistake. This hackathon's SOP already encodes Fellegi-Sunter's three zones. The winning system will be the one that turns uncertainty into REVIEW rather than into a guess.

Two gaps should shape how results are presented. No public benchmark measures LLM namesake rejection in adverse-media results, and no regulator defines DOB tolerances or acceptable miss rates. The namesake-attribution step and the date-tolerance policy are therefore the system's real risk points. They deserve the most test cases, and any claim of "zero false clears" should be stated alongside how many true matches it was tested on.
